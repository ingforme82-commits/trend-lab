## 2. 미국 시간외 시세 점검 — 먼저 해결할 데이터 표시 문제

2026-10-28 17:28 KST = 미국 동부 04:28 EDT. 프리마켓이며 정규장 개장은 22:30 KST.
Nasdaq 공식 안내: https://www.nasdaq.com/market-activity/stock-market-holiday-schedule

야후 chart API를 `includePrePost=true&interval=1m&range=1d`로 읽어 마지막 유효 분봉 종가를 확인했다.
호가·즉시 체결 보장 값이 아니며, 마지막 분봉 시각과 출처를 함께 표시해야 한다.

| 종목 | 마지막 유효 분봉(KST) | 시간외 가격(달러) | 직전 정규장 종가(달러) | 직전 정규장 종가 대비 |
|---|---|---:|---:|---:|
| SOXL | 10/28 17:31:09 | 104.01 | 101.08 | 약 +2.90% |
| KORU | 10/28 17:30:29 | 13.14 | 11.86 | 약 +10.79% |

출처: `https://query1.finance.yahoo.com/v8/finance/chart/SOXL?interval=1m&range=1d&includePrePost=true`
및 같은 경로의 KORU. 위 계산은 `시간외 가격 / 직전 정규장 종가 - 1`이다.
API의 `chartPreviousClose`는 각각 90.50, 10.89로, 이번 시간외 등락률의 기준으로 쓰면 안 된다.

사이트 live 데이터 17:27:53 KST 스냅샷은 SOXL 101.08(+11.69%), KORU 11.86(+8.91%)를 표시한다.
이는 전일 정규장 수치다. 수치 자체를 시간외 가격으로 덮어쓰지 말고 별도 세션으로 추가한다.
`tools/market_extra.py:reg_quotes`와 `tools/levetf.py`는 regularMarketPrice/regularMarketTime을 사용한다.
정규장 가격을 읽는 현재 계약은 유지하고, 별도 시간외 데이터와 표시를 만든다.

후속 구현 인수 조건:
1. 정규장 종가 / 프리마켓 / 애프터마켓을 구분하고 가격·기준가·등락률·실제 데이터 시각·출처를 함께 둔다.
2. 마지막 체결이 오래됐거나 시간외 값이 없으면 '시간외 시세 없음/지연'으로 표시한다. 전일 값에 현재 시각을 붙이지 않는다.
3. America/New_York 시간대와 거래일·휴장일을 적용한다. DST 전환, 월요일·휴일 직후, 미체결·누락을 검증한다.
4. SOXL·KORU·EWY부터 확인하고 필요 시 기존 관심 종목으로 확장한다. 분할·배당 등 기준가 조정도 확인한다.
5. Hyperliquid 가격은 거래소 지수선물과 동일 상품이 아닌 24시간 무기한 상품이다. 가격·24시간 대비 등락을 미국 ETF 시간외 체결·전일 종가 대비와 혼합하지 않는다.
6. 메인 PC가 갱신 중인지 확인한다. 이 문서만으로 시간외 수집이 추가된 것은 아니다.

## 4. 운영 판단용 방문 통계 — 현재 숫자는 확인 불가

`count.js`에 일별 브라우저 방문(v), 페이지 조회(pv), 오픈채팅(kakao), 테스트 완료(quiz), 속보·차트 클릭 집계가 있다.
`tools/visit_report.py`에는 매일 12시 보고용 코드가 있으나 이 PC에서 예약 실행·카톡 수신 성공까지 확인한 것은 아니다.

10/28 당일과 10/27 방문, 당일 페이지뷰·오픈채팅·테스트 집계 GET을 두 차례 조회했지만 시간 초과였다.
조회 실패는 방문 0명이 아니다. 과거 집계 유실 여부·서버 전체 장애 여부도 이 결과만으로 확정하지 않는다.
방문 집계 hit API와 카톡 전송은 실행하지 않았다.

현재 코드의 보완점:
- `visit_report.get()`이 모든 예외를 0으로 바꾸므로 '진짜 0 / 미생성 키 / 통신 실패'를 구분해야 한다.
- `count.js`는 요청 성공 확인 전에 localStorage의 일별 방문 표시를 저장한다. 실패한 방문이 당일 재시도되지 않을 수 있다.
- 하루 방문자는 사람 수가 아닌 브라우저 기준 추정치다. 기기 변경·시크릿 모드·저장소 차단·봇·요청 실패의 영향을 받는다.
- 카운터는 공개 엔드포인트 기반이다. 공개 페이지에 숨겨 둔 주소나 `?admin=1`을 접근 통제로 간주하지 않는다.

운영 판단 기준:
- 일별 방문은 브라우저 수 추정, 페이지뷰는 페이지 로드 수, 이벤트는 클릭/완료 횟수로 표시한다.
- 같은 날 낮까지의 숫자와 전날 하루 전체를 그대로 비교하지 않는다. 같은 시간대 또는 완료된 날짜끼리 비교한다.
- 단순 클릭 횟수/방문 수를 '가입 전환율'로 부르지 않는다. 클릭과 실제 오픈채팅 참여·스터디 신청은 별개다.
- 초기는 절대 목표 인원을 임의로 정하지 말고 1~2주 신뢰할 수 있는 기준선을 만든다. 재방문·뉴스 이용·오픈채팅 클릭의 변화를 함께 본다.
- 운영자 제외: 각 브라우저에서 `?me=1`로 방문. `?me=0`은 해제. 이 옵션은 인증 기능이 아니다.

## 8. 추가 사용자 확정 — NH 상태 확인 및 KB 자동매매 연결 검토

### 요청과 저장소 구분

사용자 후속 메시지: 'NH 자동 매매 연결인데, KB증권도 연결할 수 있나?' → '응 클로드가 이어서 진행하게 해줘'.
따라서 NH 최신 상태를 확인하고 KB 연결 검토·개발을 이어간다. 이 인계가 실계좌 자동주문 활성화를 뜻하지는 않는다.
이 문서는 공개 사이트 저장소의 인계 진입점이다. **거래 연결 구현은 market-site에서** 진행한다.
market-site의 AGENTS.md, CLAUDE.md, PROGRESS, PROJECT_CONTEXT, AGENT_LOG와 최신 git 상태를 먼저 읽는다.
기존 행동 진단 제품의 KB 조회 전용 경계를 유지하고, 개인 자동매매 도구에 별도 주문 어댑터를 둔다.

### A. NH 자동매매 최신 상태 보고

1. 메인 PC의 기존 자동매매 설정·최근 실행 로그·저널을 읽기 전용으로 확인한다. 작업명·경로는 실제 설정에서 찾는다.
2. 확인 항목: 최근 실행 시각, 예약 작업 등록·실행 여부, dry-run/mock/live 구분, 선택 환경, 전략 버전, 중단·오류·주문 결과 불명 상태.
3. `docs/25-personal-autotrade.md`와 `backend/autotrade/`, `backend/scripts/autotrade.py`, `scripts/autotrade.ps1`을 참조한다.
   `report` 모드도 실행 전 실제 코드를 읽어 비전송·읽기 전용임을 확인하고 사용한다.
4. 사용자에게 확인된 집계와 미확인 상태를 구분해 보고한다. 드라이런 판단 건수를 실제 체결 건수나 수익률로 보고하지 않는다.
5. 개인 계좌·체결 정보는 공개 사이트 저장소·터미널 로그·테스트 픽스처로 내보내지 않는다. 성과 산출 근거가 없으면 '계산 불가'로 표시한다.

### B. KB 공식 계약 및 기존 코드 호환성 확인

공식 공개 안내에서는 주문·정정·취소·잔고·체결·시세 API 제공을 확인했다.
모의투자 지원 여부·접속 주소·허용 주문 방식·IOC 지원·호출 제한은 이번 확인에서 확정하지 못했다.
다른 증권사 도메인이나 비공식 자료로 KB 모의 환경을 추정하지 않는다.

공식 확인 경로:
- https://openapi.kbsec.com/
- https://openapi.kbsec.com/guide_b2c
- https://openapi.kbsec.com/apidoc_b2c
- https://openapi.kbsec.com/howto_b2c

현재 market-site에는 `kb_auth.py`, `kb_client.py`, `kb_execution.py`, `kb_openapi_market.py` 등이 있다.
`kb_client.py`의 기존 주소는 `https://developer.kbsec.com:32484/api/v1`이다. 기존 인증 성공 기록이 최신 개인용 API와의 호환성까지 보장하지 않는다.
NH 주문 구현은 `backend/autotrade/broker.py`, 전략·엔진·저널은 같은 패키지에 있다.

1. KB 서비스 신청 계좌와 발급 앱의 API 세대를 확인한다. 키 값은 채팅·문서에 붙이지 않고 기존 로컬 보관 방식을 사용한다.
2. 최신 공식 명세에서 인증·시세·잔고·주문·정정취소·체결조회 계약을 정리하고 기존 코드와 대조한다.
3. 모의 지원 여부와 지원시장을 명시한다. 미지원·확인 불가면 KB는 조회 및 로컬 가상체결 단계까지만 진행한다. 로컬 가상체결을 KB 모의 체결로 부르지 않는다.
4. 증권사 확인이 필요한 정확한 항목만 묶어 사용자에게 요청하고, 답변 대기 중에는 합성 데이터 기반 개발·테스트를 진행한다.

### C. KB 어댑터 구현과 검증 순서

1. 기존 NH 전략을 재사용하되 `broker=nh|kb` 등 명시적인 선택 구조를 설계한다. 기존 실행 기본값과 NH 동작을 유지한다.
2. 인증·계좌·잔고·시세 조회 → 주문을 전송하지 않는 dry-run → 공식 지원이 확인된 경우 모의 검증 순서로 진행한다.
3. 계좌·환경·증권사별 저널/중복 방지 상태를 격리한다. NH와 KB 동시 가동이 주문 한도나 전략 전체 노출 한도를 우회하지 않게 한다.
4. KB의 주문접수와 실제 체결을 구분한다. 부분 체결·거절·미체결·타임아웃을 처리하고, 결과 불명 시 조회·대조 없이 재주문하지 않는다.
5. NH의 IOC·수량·총자산·주문응답 규칙을 KB에 그대로 가정하지 않는다. KB에 IOC가 없으면 지정가 미체결 잔량·취소 정책을 먼저 확정한다.
6. 공개 사이트·행동 제품 API에서 개인 자동주문을 호출하지 않도록 경계 테스트를 유지한다.
7. 합성 테스트로 증권사 선택, 키·계좌 교차사용 차단, 중복 주문, 부분 체결, 미확정 주문, 환경 누락, NH 회귀를 검증한다.
8. market-site의 ruff·mypy·pytest 필수 검증 및 문서/인계 로그를 갱신한다. 실제 호출 검증과 합성 테스트 통과를 구분해 기록한다.

### Claude 완료 보고 형식

- NH: 마지막 확인 시각 / 모드 / 실행 상태 / 확인된 집계 / 남은 문제.
- KB: 공식 지원 확인 범위 / 구현한 조회·dry-run·모의 기능 / 실제 검증 여부 / 필요한 사용자 행동.
- 시세·방문 통계: §2·§4·§5의 진행률과 미해결 사항.
- 변경 저장소·커밋·테스트 결과·다음 작업을 보고하고, 실계좌 자동주문은 별도 명시적 승인과 검증 없이 켜지 않는다.
